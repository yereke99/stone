# Stone WhatsApp Bot Dialogue Audit
Date: 2026-07-06
Scope: customer-dialogue business logic only (message understanding, OpenAI usage,
state/memory, video/hashtag examples, sales flow, STOP, admin safety).
Method: full read of cmd/main.go and internal/bot/* (live path traced from the
GreenAPI polling loop down to every send call). `go build ./...` passes.
No code was modified.

================================================================================
## 1. Executive Summary
================================================================================

How the bot works today (live configuration, .env in repo root):

1. The bot long-polls GreenAPI (cmd/main.go `runPolling`), filters/dedupes
   notifications, and passes real incoming customer messages to
   `Service.ProcessIncomingWhatsAppMessage` (internal/bot/service.go:155).
2. OpenAI IS used live, but only as a JSON "understanding layer"
   (`understandCustomerMessage`, internal/bot/understanding.go:66): it extracts
   intent + fields (niche, goal, deadline, tags...) as strict JSON. It does NOT
   write the text the customer receives.
3. The final customer reply is produced by a hand-written state machine
   (`handleSalesState`, service.go:462) that picks from a large library of
   canned RU/KK/EN template strings (prompts.go, dialogue.go, approved_flow.go).
4. A full LLM-reply mode exists (`maybeGenerateConversationReply`,
   llm_reply.go:20, using the polished sales prompt `SystemPrompt` in
   prompts.go:5) but it is gated behind env var BOT_LLM_REPLY_ENABLED which
   defaults to FALSE and is NOT set in .env. In the live deployment the
   polished sales prompt is dead code.

Main problems:

* P0 — MAX_OPENAI_OUTPUT_TOKENS=350 is almost certainly too small for the
  required strict JSON schema (22 mandatory extracted_fields + message_meaning
  + reply_text + answered_questions...). When output is truncated the JSON
  parse fails and the bot silently falls back to the regex analyzer
  (`AnalyzeCustomerMessage`, analysis.go:152). In that mode the bot is exactly
  the "rule-based/stupid" bot described in the complaint. (UNCERTAIN how often
  this fires — needs log check for "openai customer understanding failed".)
* P0 (UNCERTAIN) — model `gpt-5.5` is called with `temperature` on the
  Responses API (openai/client.go:283-284). If this model rejects the
  temperature parameter (as several reasoning-class models do), EVERY analyzer
  call fails with HTTP 400 and the bot runs 100% on regex rules. This must be
  verified in production logs; it would explain all "bot is dumb" symptoms.
* The "Никакой" bug from the complaint is defended in the CURRENT code in
  three independent places (deterministic guard, AI prompt rule, ApplyAnalysis
  validity guard) — see section 6, Example B. If it still reproduces in
  production, the analyzer call is failing (see the two P0s above) AND the
  running build predates these guards, or an AI paraphrase slips through the
  guard (possible, see §5 overwrite risks).
* Human-likeness is limited by design: every reply the customer sees is a
  static template. The niche/goal qualification question has essentially one
  phrasing; FAQ answers are canned; the "understanding" quality of OpenAI is
  only used to route between templates and to fill fields.
* The history-guard subsystem (protecting old/legacy chats, with its own
  OpenAI classifier) is configured in config.go but NEVER wired:
  `SetHistoryGuard` has no caller in cmd/main.go. Only DB-stored legacy flags
  (from the offline importer) still silence chats.

Biggest risks, in order: (1) analyzer silently failing → regex-only behavior;
(2) overly broad customer opt-out substrings ("не надо", "передумал")
permanently suppressing live leads; (3) only-2-videos cap and the
niche+goal precondition delaying relevant examples; (4) manual admin replies
do NOT pause the bot (only an explicit "стоп" from the business phone does).

## 2. Real Incoming Message Flow
================================================================================

Entry point and polling
-----------------------
* cmd/main.go `main` (43): builds GreenAPI client, OpenAI client, SQLite
  conversation store, `bot.NewService`, sets delayed-package options, then
  `runPolling`. NOTE: `botService.SetHistoryGuard(...)` is never called →
  history-guard runtime disabled (live).
* cmd/main.go `runPolling` (117): infinite ReceiveNotification loop with
  exponential backoff (1s→10s). LIVE.
* cmd/main.go `processNotification` (159): the gatekeeper. LIVE.
  - `outgoingMessageReceived` (manual send from the business phone) →
    `handleOutgoingPhoneWebhook` (383): journals the message into
    whatsapp_messages and checks `isManualAdminStopNotification` →
    `MarkManualStop`. It never generates replies.
  - `outgoingAPIMessageReceived` (bot's own sends) → logged and deleted,
    fully ignored. The bot cannot parse its own messages as customer input.
  - Everything else goes through `shouldProcessNotification` (347):
    * only `incomingMessageReceived`
    * timestamp required; drops messages older than service start minus a
      2-minute grace (`isStartupStaleNotification`, 606) and older than
      BOT_MAX_MESSAGE_AGE_SECONDS=120 (`isStaleNotification`, 598)
    * WhatsApp groups always skipped ("whatsapp_group_automation_disabled")
    * only text or media messages; empty text rejected.
* Deduplication: `notificationMessageKeys` (573) builds `chatID|messageID` or
  a sha256 fallback key; `ConversationStore.BeginIncomingMessageProcessing`
  (sqlite_store.go:462) inserts into whatsapp_messages with a UNIQUE
  dedupe_key; duplicates/in-flight messages are dropped. LIVE.
* Suppression check BEFORE the bot service:
  `conversationStore.IsSuppressedPhoneOrChatID` (suppression.go:34) — if the
  phone/chat is in whatsapp_automation_suppression, the incoming text is still
  saved to the transcript (`AppendMessage` + `MarkIncoming`) but no processing
  and no OpenAI call happens. LIVE.

Bot service entry
-----------------
* `Service.HandleIncomingMessage` → `ProcessIncomingWhatsAppMessage`
  (service.go:151/155). LIVE. Step by step:
  1. suppression re-check (`isAutomationSuppressed`) and group-chat check
     (`isUnsafeCustomerWhatsAppChatID`, whatsapp_safety.go:32).
  2. per-chat mutex `lockChat` (2422) — serializes a chat.
  3. sender display name saved into conversation + Lead.ClientName (207-214).
  4. language detected once and persisted (`detectLanguage`, 2061 —
     Cyrillic→ru, Kazakh markers→kk, default ru).
  5. media without text → `handleIncomingMediaContext` (1177): stores a
     placeholder ("[фото] ..."), replies with `NonTextFallbackText` ("напишите
     текстом...") unless the same fallback was the last reply.
  6. `AppendMessage(user)` + `MarkIncoming` — transcript + last-incoming.
  7. `isExplicitOptOutText` (3398) → `stopAutomationSilently` (1039) →
     permanent row in whatsapp_automation_suppression. No reply is sent.
  8. `isConversationClosedForAutomation` (safety.go:17) → message saved,
     silence (handed-off/stopped/legacy chats).
  9. `maybeApplyHistoryGuard` (history_guard.go:122) — the *runtime* guard is
     disabled (source==nil, Enabled=false), but `shouldSilenceForStoredHistory`
     (history_guard.go:445) still silences chats whose legacy classification
     was written to the DB by the offline importer
     (cmd/import_historical_contacts). PARTIALLY LIVE.
  10. `understandCustomerMessage` (understanding.go:66) — the OpenAI analyzer
      with deterministic fallback. LIVE. Details in §3.
  11. Post-processing of the analysis: FAQ override (`detectFAQIntent`,
      approved_flow.go:117), quoted-reply package detection
      (`detectPackageFromReplyContext`, reply_package.go:8), brief-state
      normalization, `isBusinessRelevantMessage` gate (approved_flow.go:176)
      — off-topic messages are silently ignored.
  12. `lead.ApplyAnalysis(analysis)` + `store.UpdateLead` (analysis.go:400) —
      guarded merge of extracted fields into the persistent lead.
  13. `maybeGenerateConversationReply` (llm_reply.go:20) — DEAD in live env
      (BOT_LLM_REPLY_ENABLED unset → false). When enabled it would produce the
      final reply from `SystemPrompt` for most next_actions.
  14. `handleSalesState` (service.go:462) — the live reply engine (see §8).

Sending and persistence
-----------------------
* All text replies go through `sendAndRemember` (service.go:1468): re-checks
  suppression/manual-stop/closed state, runs the final-reply validation gate
  (`validateOutgoingReply`, final_reply_guard.go:13 — blocks forbidden
  discount promises, celebrity-voice promises, and questions about
  already-known fields), enforces "package example videos must be sent before
  the format question" (`needsPortfolioExamplesBeforeFormatQuestion`, 2326 +
  `ensurePortfolioExamplesSentBeforeFormatQuestion`, 1588), dedupes identical

  (`LogOutgoingMessage`), appends to transcript, marks asked fields
  (`MarkAskedFields`), updates stage (`UpdateState`), and notifies admins

* Videos go through `sendVideosWithCaptions` (service.go:1657): per-file
  suppression re-check, `ShouldSendVideo` repeat guard, file existence check,
  caption resolution (explicit map → `OfferByVideo(...)` package caption),
  GreenAPI `SendFileByUpload(filePath, caption)` (one WhatsApp message with
  media + caption), `MarkVideoSent`, `RecordOutgoingPackageMessage`, 1.5s
  delay between files (`videoSendDelay`).
* Persistence: every mutation runs `persistConversationLocked`
  (sqlite_store.go:318) — whole Conversation struct is serialized into
  whatsapp_clients.conversation_json (including Messages history, Lead,
  AskedFields, SentVideoFiles), plus flat columns (state, niche, goal,
  deadline, selected_package, followups...). All messages in/out are also
  journaled in whatsapp_messages.

* `fieldListSchema` (openai/client.go:824) — unused.

## 3. OpenAI / ChatGPT Usage
================================================================================

Q: Is OpenAI generating the final customer reply, or only extracting JSON?
A: In the live configuration OpenAI ONLY extracts JSON (intent + fields +
   recommended action). The customer-visible text always comes from templates.
   The analyzer's reply_text is ignored. The full LLM-reply mode exists but is
   off (BOT_LLM_REPLY_ENABLED defaults false, absent from .env;
   service.go:104-112, llm_reply.go:21).

Which functions call OpenAI (internal/openai/client.go):
* `Client.AnalyzeCustomerMessage` (268) — LIVE, called once per incoming text
  message from `understandCustomerMessage` (understanding.go:76), 8s timeout,
  temperature capped to 0.2 (`analysisTemperature`), max_output_tokens =
  min(MAX_OPENAI_OUTPUT_TOKENS=350, 1200) = 350, strict json_schema
  `stone_customer_understanding`.
* `Client.GenerateSalesReply` (189) — DORMANT (only from the disabled LLM
  reply path), strict json_schema `stone_sales_response` (same shape).
* `Client.ClassifyHistoryGuard` (333) — DEAD (history guard not wired).

What the analyzer receives (`customerUnderstandingPayload`,
understanding.go:148) — this is genuinely rich context:
* current_message (text, id, timestamp);
* quoted_context — quoted bot text/caption when the customer replied to a
  specific message;
* recent_messages — the LAST 10 transcript messages, BOTH bot and customer
  roles, with timestamps (`recentUnderstandingMessages`, 255). YES, previous
  bot messages are included;
* pending_questions — the last bot question + which fields it asked, filtered
  to still-unknown fields (`pendingUnderstandingQuestions`, 284);
* question_answer_pairs — pairs the current customer text with the quoted (or
  last) bot question and the expected field(s)
  (`questionAnswerPairsForUnderstanding`, 302). This is exactly the mechanism
  that lets the model know "Никакой" answers "Какой формат вам понравился?";
* known_state / conversation_state — `conversationPromptJSON` (service.go:2195):
  stage, lead_status, full LeadState, completed_fields, asked_fields,
  sent_videos + sent_video_files (yes, already-sent examples are included),
  packages_sent, brief flags, conversation_summary, last incoming/reply text
  and (again) recent messages;
* official_packages with names/prices/filenames;
* last_bot_question + asked fields; current_missing_fields.

So: recent history YES (10 messages), bot messages YES, saved state YES,
sent videos YES, sales stage YES.

Does OpenAI return structured JSON / is it validated?
* Yes — the request uses the Responses API `text.format=json_schema` with
  `strict: true` and `additionalProperties: false`
  (`customerUnderstandingSchema`, openai/client.go:518). The Go side
  unmarshals and then `customerUnderstandingToAnalysis` (understanding.go:382)
  validates confidence ∈ [0,1], drops all extracted fields when confidence
  < 0.35, re-validates every field (`isValidNiche`, `normalizeGoal`,
  `normalizeDeadline`, `normalizePackageInterest`...), and respects
  do_not_overwrite_fields (`protectedFieldsMap`).

What happens on bad JSON / errors / timeout?
* Any HTTP error, schema failure, JSON parse failure or 8s timeout →
  WARN log + deterministic fallback `AnalyzeCustomerMessage` (analysis.go:152),
  a large regex/keyword analyzer. The dialogue continues, but with noticeably
  cruder understanding. There is no retry and no alerting.

Schema/struct mismatches (important):
* The strict schema does NOT include top-level `niche/goal/...`, `sentiment`,
  `state_update`, `needs_manager`, `ready_for_questionnaire`,
  `asks_for_food_examples`, `asks_for_more_options`, `quantity`, `reply_plan`.
  Those struct fields (openai/client.go:60-108) can never be populated by the
  live schema; all code branches reading them
  (understanding.go:551-580 sentiment/state_update; "asks_examples",
  "negative_reaction", "frustration", "ready_to_order", "choose_package"
  intent cases at 483-549) are unreachable from the live analyzer and only
  work for the deterministic fallback / legacy tests. Consequences:
  - AI can flag a human handoff ONLY via needs_human (which IS in schema);
  - AI can never trigger the "silent stop on negative sentiment" branch;
  - frustration/negative detection is purely regex
    (`isFrustrationComplaint`/`isNegativeReaction`, analysis.go:1793/1784).
* The intent enum the model may return (conversationIntentSchema, 584) and
  the switch in `customerUnderstandingToAnalysis` overlap only partially —
  e.g. model-returnable "quantity_answer" maps to discount handling, but
  "objection" maps to... nothing (falls to default IntentOther) — the word
  "objection" is missing from the switch, so an AI-detected objection is
  downgraded to "other". (Deterministic `containsObjection` still catches
  "дорого".)

Token budget problem (P0 candidate):
* MAX_OPENAI_OUTPUT_TOKENS=350 (.env) also caps the analyzer
  (`minPositive(c.maxOutputTokens, 1200)`, openai/client.go:283). The
  required response includes ALL 22 extracted_fields keys, message_meaning,
  reply_text, portfolio_tags, missing_fields, answered_questions... A typical
  full response is 300-600+ tokens. Truncated output → parse error → regex
  fallback. This silently degrades exactly the cases with the most content
  (long first messages like Example A).

Ratings (1-10):
* Context understanding quality (as designed): 8 — payload is excellent.
  Effective in production: 5-6 (fallback risk, token cap, unverified model
  params).
* Prompt quality (analyzer prompt): 8 (see §4).
* State safety: 7 — do_not_overwrite + validity guards + confidence floor;
  minus for unconditional overwrites of secondary fields (§5).
* Human-like reply quality: 3-4 — replies are canned templates; the analyzer's
  human-sounding reply_text is discarded.
* Risk of misunderstanding customer messages: 5 (moderate) — good when the
  analyzer works, regex-only when it doesn't; short/ironic/atypical answers
  outside the whitelists degrade hard.

## 4. Prompt Quality Review
================================================================================

Prompt 1: `customerUnderstandingSystemPrompt` — internal/bot/understanding.go:15
* Status: LIVE (used on every text message).
* Task: strict-JSON understanding layer; extract fields, classify intent,
  suggest recommended_action/next_action/portfolio_tags.
* Sales context: explained well (48h AI ads, what Go enforces, official
  prices Test 35k / Basic 50k / Standard from 75k).
* Short answers: EXPLICITLY teaches "никакой" (line: `If the bot asked "Какой
  формат вам понравился?" and the customer answers "Никакой", this is
  negative_selection... must put "niche" in do_not_overwrite_fields`), plus
  "нет, не знаю, ок, да, потом, сейчас, завтра, посмотрю must not overwrite
  niche or goal", "20-30 is quantity not budget", URL-only ≠ goal, "примерно"
  ≠ examples request.
* Overwrite prevention: yes — do_not_overwrite_fields is a first-class output.
* Strict JSON: yes; schema enforced server-side.
* Few-shot examples: yes, 5 concrete ones (construction mixtures multiline,
  reference link, link+goal, Vin Diesel voice, AI actors copyright).
* Weaknesses:
  - It asks for fields the schema forbids (answered_questions is in schema,
    fine; but the "Output contract" mentions language etc. — consistent), yet
    the *intent list in prose* matches the schema while the Go mapping switch
    misses "objection" (see §3) — a prompt-consumer mismatch, not a prompt bug.
  - No explicit rule for "стоп бот" (handled upstream in Go, acceptable).
  - No instruction about what to do when recent_messages contradict
    known_state (e.g. admin edited data) — low priority.
  - reply_text is requested and then thrown away — wasted tokens (against a
    350-token cap this matters).
* Verdict: 8/10 — one of the strongest parts of the codebase.

Prompt 2: `SystemPrompt` (the polished RU sales-manager prompt) —
internal/bot/prompts.go:5
* Status: DEAD in live config (only `GenerateSalesReply` path, env-gated off).
* Quality if enabled: good sales framing ("не анкета-бот", answer direct
  question first, never re-ask known fields, never ask deadline in first
  qualification, negative_selection rule for "никакой", real-estate/tourism
  tag rules, price discipline, copyright safety, defer etiquette). It also
  demands strict JSON with the same schema.
* Weaknesses: mixes RU and EN instructions; duplicates the understanding
  prompt (two sources of truth to keep in sync); the short brief text inside
  the prompt differs from the live BriefText template (four questions vs
  three) — if ever enabled, the bot would produce a second brief variant.
* Verdict: 7/10, but currently irrelevant to customers.

Prompt 3: history-guard classifier prompt — internal/openai/client.go:334
* Status: DEAD (subsystem not wired). Minimal but adequate for its job.

Everything else the customer reads is NOT a prompt but a static template:
prompts.go (greeting, price, brief, handoff, objection...), dialogue.go
(package prices/details, quantity discount), approved_flow.go (FAQ answers,
format question, questionnaire reminder, weekly follow-up), service.go
(negative-selection texts, cases texts, AI-work intros), offers.go (video
captions). These are decent copy but fixed — the bot will repeat the same
sentence in the same situation every time.

## 5. Conversation State / Memory
================================================================================

Where fields live — `LeadState` (analysis.go:68) inside `Conversation`
(store.go:43), persisted per chat in SQLite whatsapp_clients (flat columns +
full conversation_json blob):
* niche → Lead.Niche (+ flat column `niche`)
* goal → Lead.Goal (+ column `goal`)
* deadline → Lead.Deadline (+ column `deadline`)
* budget → Lead.Budget (JSON blob only)
* video quantity → Lead.VideoQuantity
* selected package → Lead.SelectedPackage + Conversation.SelectedLevel
  (+ column `selected_package`)
* sent examples → Conversation.SentVideos (by level), SentVideoFiles
  (by file path incl. ai-works paths, with timestamps),
  OutgoingPackageMessages (messageID → package metadata, used to resolve
  quoted replies to a specific package video)
* asked/completed → AskedFields / CompletedFields maps
* last bot question → LastReplyText/LastReplyAt; last customer text →
  LastIncomingText/LastIncomingAt
* transcript → Conversation.Messages, capped at the LAST 10 messages
  (`AppendMessage`, store.go:496, historyLimit=10). The complete history is
  additionally journaled in the whatsapp_messages table but is NEVER read
  back for prompting (only for dedupe) — so "reconstruct last 5-10 messages"
  = YES (exactly 10), more than 10 = only via SQL, not used.

Can the bot know what question it asked before the customer replied? YES —
LastReplyText + AskedFields + `fieldsAskedByMessage` (service.go:2453) and it
forwards that as pending_questions / question_answer_pairs to OpenAI.
Can it pair "никакой" with the format question? YES (same mechanism; plus the
quoted context when the customer replies to the message).

Repeat-question protection:
* AskedFields is recorded on every send; `validateOutgoingReply`
  (final_reply_guard.go:13) actively REWRITES an outgoing reply that asks
  about an already-known field (`knownFieldsAskedByReply`) into the next
  useful question; `RecentlySentReply` blocks resending identical text within
  2 minutes; the understanding prompt forbids re-asking. This is solid.

Overwrite analysis — `LeadState.ApplyAnalysis` (analysis.go:400):
* PROTECTED: Niche and Goal are replaced only by values passing
  `isValidNiche`/`isValidGoal` + `isNonNicheCandidateText` (qualification.go:86,
  analysis.go:1869). A stored valid niche can never be wiped by "никакой",
  "да", "не знаю", a question, a greeting, or a timing word. Deadline
  similarly guarded. During brief answering (Intent=BriefAnswer),
  qualification fields are frozen entirely (updateQualificationFields=false).
* AI-side protection: `customerUnderstandingToAnalysis` re-validates and
  respects do_not_overwrite_fields; confidence<0.35 drops extraction.
* DANGEROUS overwrites (any new non-empty value wins, valid→valid):
  - Niche → another *valid-looking* niche. An AI paraphrase like
    "никакой формат" or "клиент недоволен" passes `isValidNiche` (≥2 letters,
    not in the short-reply blacklist) and would REPLACE a good niche.
    isNonNicheCandidateText only blocks known short forms.  << the most
    realistic remaining path to the reported bug >>
  - ProductOrService, TargetAudience, StrongSide, Offer, Budget,
    VideoQuantity, VoicePreference, CampaignContext, HookIdea (analysis.go:
    428-466): unconditional overwrite, no validity check, not protected by
    do_not_overwrite handling for most of them (budget/quantity/audience are
    protected AI-side but not fallback-side).
  - `recordBriefMessage` (active_flow.go:113) overwrites ProductOrService/
    TargetAudience/StrongSide/Offer from every brief message.
  - `Conversation.DisplayName`→Lead.ClientName only when empty (safe).
* `sanitizeLeadForQualification` (qualification.go:61) runs on every store
  Update and CLEARS invalid niche/goal/deadline/package — good self-healing,
  but it also means a junk value that passed validation once will be asked
  again only if it later fails validation (it won't), so junk persists.

Restart safety: full Conversation JSON (incl. Messages, SentVideoFiles,
AskedFields) is reloaded at startup (`loadConversations`, sqlite_store.go:261).
Memory is NOT lost on restart.

Missing:
* No long-term memory beyond 10 transcript messages for the LLM.
* whatsapp_messages journal unused for context reconstruction.
* No per-field provenance/confidence stored (can't tell "niche came from a
  weak guess" later).

## 6. Customer Understanding Evaluation (Examples A–E)
================================================================================

Example A — "Здравствуйте. Я хочу продать земельный участок в пригороде. Мне
нужна визуализация перспектив и съёмка с дрона"
* Deterministic path (works even if OpenAI fails):
  - `knownNicheFromText` (analysis.go:2213) has an EXPLICIT rule:
    "земельный участок" → "недвижимость / земельный участок". Niche set.
  - `extractGoal` (750): "хочу продать" → hasExplicitGoalSignal → normalizeGoal
    "продать" → "рост продаж". Goal set.
  - `portfolioTagsFromText` (ai_works.go:218): "земель/участ"→real_estate,
    property, land; "дрон"→drone; "визуализац/перспектив"→visualization.
* AI path adds the same tags per prompt rules (real_estate/land/drone/
  visualization are dictated in both prompts).
* Flow: niche+goal valid → `shouldSendRelevantAIWorkExamples` (service.go:2917)
  = true → `sendRelevantAIWorkExamples` (2962): intro "Понял вас: ... нужна
  визуализация перспектив и съёмка с дрона для продажи. Сейчас отправлю
  подходящие примеры по недвижимость / земля." then top-2 videos.
  Ranking: realtor_land.mp4 (tags real_estate+property+land+drone+
  visualization+realtor) scores ~5, wins; second is real_estate.mp4 (~score 3).
* Verdict: PASSES — does not ask "какая ниша?", sends 2 relevant examples with
  captions. Two caveats: (1) it never addresses that Stone does NOT do real
  drone shooting (AI video without filming) — no template corrects the
  misconception; (2) if the analyzer call fails AND the greeting-first branch
  triggers on a *new* chat, the state machine still routes to relevant
  examples because both fields extracted deterministically.
* Responsible code: understanding.go:66, analysis.go:2213/750,
  ai_works.go:138/218, service.go:538/2917/2962.

Example B — Bot: "Какой формат вам понравился?" Customer: "Никакой"
* Deterministic: `isNegativeFormatSelection` (analysis.go:1599) matches
  "никакой" exactly → Intent=negative_selection. `extractNiche` returns ""
  ("никакой" is in `isNonNicheShortReply`, 1494, → isNonNicheCandidateText).
* AI: prompt rule forces negative_selection + do_not_overwrite ["niche","goal"];
  even if it returned niche="никакой", `isValidNiche`+`isNonNicheCandidateText`
  filtering in customerUnderstandingToAnalysis (understanding.go:398) drops it.
* Flow: handleSalesState → `handleNegativeSelection` (service.go:2950):
  - niche+goal known → "Понял, из тех форматов ничего не выбрали. Тогда
    отправлю примеры ближе под вашу задачу: <ниша>." + relevant examples;
  - fields missing → politely asks ONLY the missing field, WITHOUT saving
    "никакой" anywhere;

## 7. Portfolio / Hashtag / Video Sending Logic
================================================================================

Two separate video systems:

A) Package/format videos — video/video_level_{1..4}.mp4 (offers.go:6).
   Sent by `ensurePortfolioExamplesSentBeforeFormatQuestion` (levels 1-3, each
   with a full package caption: title + description + price, offers.go:141)
   right before the first "Какой формат вам понравился?", by
   `selectPackageWithoutOpeningBrief` (the chosen package's video), and
   video_level_4.mp4 as the weekly follow-up creative
   (`sendWeeklyDiscountFollowup`, followup_actions.go:68).

B) Niche examples ("hashtag" videos) — ai-works/<category>/*.mp4.
   * Storage: files on disk; metadata is HARDCODED in
     internal/bot/ai_works.go — `aiWorksByCategory` (27; 15 categories,
     58 files — verified to match the disk exactly), category tags
     `aiWorkCategoryTags` (120), plus per-file extra tags in `aiWorkVideo`
     (307; e.g. realtor_land.mp4 += land, drone, visualization, property).
   * Tag sources for a customer: AI `portfolio_tags` + keyword scan of lead
     fields and current analysis (`aiWorkTagsForLead`, 190;
     `portfolioTagsFromText`, 218 — RU/EN substring rules for real estate,
     land, drone, visualization, tourism, auto, fashion, food, medicine,
     logistics). `normalizePortfolioTags` (263) lower-cases, maps aliases
     (travel→tourism, car→auto, clinic→medicine...).
   * Matching type: exact intersection of normalized tag sets, scored by the
     COUNT of shared tags (`aiWorkMatchScore`, 337). Not fuzzy, not embedding,
     keyword-driven. OpenAI helps only by supplying portfolio_tags.
   * Selection: `selectAIWorkExamples` (138) scores every video, stable-sorts
     by score desc then map order, cuts to `limit`.

THE LIMIT — direct answers to the required questions:
* «Если по хэштегу найдено 1 видео — сколько отправляется?»  → 1.
* «Если найдено 2 видео — сколько отправляется?»            → 2.
* «Если найдено 3 видео — сколько отправляется?»            → 2 (top-2 by
  score; the third is silently dropped).
* «Есть ли лимит?»  → Да: `maxAIWorkExamples = 2`.
* «Где этот лимит в коде?» → internal/bot/ai_works.go:11 (constant) and both
  call sites pass it: internal/bot/service.go:2938 and :2963
  (`selectAIWorkExamples(conversation.Lead, analysis, maxAIWorkExamples)`).
* «Можно ли отправить все найденные или только top N?» → Сейчас только top-2.
  `selectAIWorkExamples` already accepts a `limit` parameter (limit<=0 →
  default 2), so sending all matches is a one-line change at the call sites;
  no other code assumes exactly 2.

No matches / fallback:
* 0 matching videos → `shouldSendRelevantAIWorkExamples` returns false; the
  state machine continues (qualification question or format question). In the
  negative-selection handler → `negativeSelectionFallbackText`. There is NO
  generic fallback example video (the "closest related example" caption
  exists — `aiWorkCaption` exact=false — but only fires when some tag matched
  with low specificity, e.g. category matched via a broad tag).

Duplicates & repeats:
* `sendRelevantAIWorkExamples` skips files already in SentVideoFiles (2971);
  `ShouldSendVideo` (store.go:966) blocks re-sends unless the customer
  explicitly asks again (`isExplicitVideoRepeatRequest`).
* If ALL matching examples were already sent, `shouldSendRelevantAIWorkExamples`
  = false and — in the negative-selection case with complete fields — the
  intro branch can degrade to the generic fallback text. Edge case: race
  between the two `selectAIWorkExamples` calls is harmless (same inputs).

Captions / message shape:
* Video + caption ARE one WhatsApp message: GreenAPI `SendFileByUpload`
  includes `caption` in the multipart body (greenapi/client.go:190-207).
* ai-works videos get a short RU/KK/EN caption ("Подходящий пример под вашу
  задачу: недвижимость / земля." or the honest "Точного кейса нет, отправляю
  ближайший по смыслу пример"), package videos get the full offer text.
* The flow for examples is: 1 intro text message ("Понял вас: <ниша>...
  Сейчас отправлю...") → video1+caption → 1.5s pause → video2+caption. That
  reads human: acknowledge → deliver, with per-video captions. Not broken.

Gating problem (impacts perceived intelligence):
* `shouldSendRelevantAIWorkExamples` (service.go:2917) requires BOTH niche and
  goal to be valid AND the questionnaire flow not started AND intent not in a
  long exclusion list. A customer who states only the niche ("у нас туризм")
  gets the goal question first, and generic package videos may arrive (via
  the 15-minute auto-package follow-up or a price question) BEFORE any
  tourism example. Relevant examples can also be permanently skipped once
  QuestionnaireOfferSent=true.

## 8. Sales Flow Logic
================================================================================

Stage model: neutral_new → awaiting_qualification → packages_presented →
awaiting_questionnaire_confirmation → brief_requested → handoff_required /
handed_off (+ stopped/opt_out/legacy states). `clientStateForConversation`
(sqlite_store.go:625) derives the effective state from flags.

1. First message (`sendGreetingAndSchedule`, followup_actions.go:34): greeting
   with "от 35 000 тг" + asks niche and goal (QualificationGreetingText),
   schedules auto-packages follow-up (default 15 min,
   NEW_LEAD_AUTO_PACKAGES_* — enabled by default).
2. Niche/goal detection: OpenAI analyzer + regex extractors merge into
   LeadState; qualification asks ONLY niche+goal (deadline deliberately never
   asked — MissingCoreFields, analysis.go:519; several regression tests pin
   this).
3. Examples: relevant ai-works examples when niche+goal known (see §7);
   otherwise the three package videos with price captions are sent right
   before the first format question
   (`ensurePortfolioExamplesSentBeforeFormatQuestion`).
4. Price/packages: format question "Какой формат вам понравился?" →
   `handlePackagesPresented` (service.go:732) routes package selection, price
   questions, objections ("дорого" → Test-package pitch), portfolio repeats,
   business links.
5. Questionnaire: offer ("Отправить анкету?") → confirmation handler
   (`handleQuestionnaireConfirmation`, 809) → `sendQuestionnaireAndAwaitBrief`
   (914) sends the 4-question brief (BriefText).
6. Brief: `handleBriefRequested`/`recordBriefMessage`/`briefCompletionStatus`
   (active_flow.go) — keyword heuristics decide which of product/strength/
   client/offer is still missing and ask exactly one next question; numbered
   answers complete instantly.
7. Handoff: `completeBriefAndHandoff` → "Спасибо, бриф получили. Передаю
   менеджеру..." → stage handoff_required → `notifyAdminsIfNeeded`
   (service.go:1755) sends the admin (ADMIN_CHAT_IDS) a WhatsApp lead card
   (name, phone, niche, goal, package, summary, wa.me link) once per chat;
   automation closes (AutomationClosed=true).
   Explicit "оператор/менеджер" → `sendHumanHandoff` immediately.
   `askMissingBeforeManager` blocks handoff until niche+goal+package known.
8. Follow-ups (delayed_packages.go): packages after 15 min of silence after
   greeting; questionnaire offer 1h after packages; reminder after 24h;
   weekly "новый AI-проект" video after 7 days. All follow-ups re-check
   suppression/stop/closed state and cancel when the client replied.

Problems observed:
* Silent no-reply branches: `presentPortfolioAndPackages` returns nil when
  packages already sent (service.go:692); off-topic gate drops messages;
  `handleBriefRequested` swallows bare "ок". Deliberate anti-spam, but the
  customer sometimes gets NO answer at all — reads as "bot ignored me".
* Only one phrasing per situation → repetition across days feels robotic
  despite the anti-repeat validation gate.
* Too-early questionnaire pressure: after packages, ANY agreement ("да")
  moves toward the questionnaire; an FAQ answer is always suffixed with
  "Отправить анкету?" once the offer stage is reached.
* Early price is fine (greeting includes it), but a cold "сколько стоит?"
  gets a greeting template rather than the 3-package price answer.
* Field extraction on the regex path is whitelist-based: an unknown niche
  word ("продаём септики") that misses every marker can bounce ("Подскажите,
  что продаёте...") even though the customer just said it — the OpenAI layer
  usually rescues this, IF it is working.
* Hardcoded replies ignoring OpenAI: by design ALL replies ignore OpenAI's
  reply_text (live). The recommended_action is only partially honored
  (send_relevant_examples → IntentPortfolioRequest mapping).

## 9. STOP / Suppression Logic
================================================================================

Supported customer STOP triggers (`isExplicitOptOutText`, service.go:3398):
* exact (after normalization): "стоп", "stop", "unsubscribe", "отмена",
  "cancel";
* `IsAdminStopCommand` (manual_stop.go:30): "stop", "стоп", "stop bot",
  "стоп бот" — with lower-casing, punctuation/whitespace stripping
  (`NormalizeAdminStopCommand`) and Cyrillic↔Latin confusable folding
  (`stopConfusableFolds`) so "sтоп bот" style mixes still match; plus exact
  "отключить", "не писать", "хватит", "остановить"...;
* substrings: "не пишите", "не надо", "не интересно", "не актуально",
  "передумал", "отписаться", "жазбаңыз", "керек емес", "not interested"...

"стоп бот" → WORKS (exact fold match). Case-insensitive: YES. Punctuation and
extra spaces: handled. RU/EN/KK variants: yes (KK partially).

Effect (`stopAutomationSilently`, service.go:1039): opt_out stage, Stopped,
AutomationClosed, StoppedBy=customer, permanent INSERT into
whatsapp_automation_suppression (suppression.go:63), follow-ups cancelled.
Suppression is checked BEFORE OpenAI (cmd/main.go:292 — suppressed incoming is
only journaled) and before every outgoing send (sendAndRemember,
sendVideosWithCaptions, sendCustomerWhatsAppFile, follow-up scheduler).

Admin manual stop: an outgoing message typed from the business phone
containing a stop command → `handleOutgoingPhoneWebhook` → `MarkManualStop`
(store.go:738) → StopReason=manual_admin_stop; `isConversationManuallyStopped`
(safety.go:46) then blocks every send path. Outgoing API (bot) messages can
never trigger it (cmd/main.go:211 branch ignores them for stop logic).

Can the bot re-enable itself? NO code path deletes suppression rows or clears
Stopped/OptOut. `MarkIncoming` even re-asserts Stopped from the stage
(store.go:300). `ReopenIncompleteHandoff` exists but is never called (dead).
Migration even force-stops all group chats and seeds several protected phone
numbers (sqlite_store.go:164-188).

Where it can fail:
* FALSE POSITIVES, not false negatives: because opt-out uses substring
  matching, ordinary sentences like "не надо анкету, просто скажите цену",
  "мы передумали насчёт стандарта, давайте тест", "это не актуально до
  понедельника" PERMANENTLY silence the lead with no notification to anyone.
  This is the biggest STOP-related business risk (lost leads, silent).
* `isNegativeReaction` (analysis.go:1784) also matches substring "стоп" and
  "не надо" → silent stop through the negative-reaction branch
  (service.go:479) — same overreach.
* Suppression queries run on every message and swallow DB errors as
  "not suppressed" (suppression.go:97-101) — fail-open on DB failure
  (low likelihood).

## 10. Admin / Outgoing Message Safety
================================================================================

* Own bot messages: arrive as `outgoingAPIMessageReceived` → logged/deleted,
  never parsed as customer input (cmd/main.go:211). Bot replies enter customer
  state only as role="assistant" transcript entries (sendAndRemember →
  AppendMessage). SAFE.
* Admin manual replies (from the business phone): arrive as
  `outgoingMessageReceived` → journaled into whatsapp_messages
  (`LogOutgoingWhatsAppMessage`) and checked ONLY for stop commands. They are
  NOT added to Conversation.Messages, do NOT pause automation, and do NOT
  reset follow-ups. Consequences:
  - The bot CAN keep auto-replying in a chat the admin has taken over,
    unless the admin sends "стоп" (or the chat had reached a handoff/closed
    state, which does close automation).
  - The OpenAI context never sees what the admin manually wrote — the model
    may re-ask something the admin already answered.
* Group chats: quadruple-protected (incoming skip, outgoing block, conversation
  force-stop `disableGroupConversationAutomation`, DB migration cleanup).
* Admin notifications go only to normalized ADMIN_CHAT_IDS via
  `sendManagerWhatsAppMessage` with a purpose gate (whatsapp/safety.go),
  and are one-shot per chat (AdminNotifiedAt / AdminOperatorNotifiedAt).
* After handoff (`sendHumanHandoff`/`completeBriefAndHandoff`) automation is
  closed; `outgoingStageAllowsClosedAutomation` (service.go:1447) allows only
  the final handoff texts through. The bot does not send automatic replies
  after a *flow-triggered* handoff — but again, a purely manual admin
  takeover without a stop command does not close anything.
